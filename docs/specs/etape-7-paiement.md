# Étape 7 — Paiement en ligne, en mode test

Références : docs/brief.md partie 10 (paiement), 14 (événements `paiement_initie`, `paiement_reussi`), 15.1 (tests de lib/paiement.ts) ; docs/PLAN.md ajustement 6 (logos de paiement).

Rappel du principe (10.1) : aucun paiement au moment de la demande. Une fois le prix confirmé, le client paie soit en ligne par un lien signé que nous lui envoyons, soit sur place après la prestation. Deux micro-entreprises, deux encaissements : paramètre `encaisseur = A | B`, deux comptes Stripe (et deux comptes PayPal en secours).

Contrainte de ce conteneur : api.stripe.com, paypal.com et les sites des émetteurs de cartes sont injoignables d'ici. Toute la logique doit donc être testable sans réseau (client Stripe injecté ou simulé dans les tests, interception des requêtes dans Playwright). Ne prétends jamais avoir testé un vrai paiement.

## 1. Liens de paiement signés — `src/lib/paiement.ts` (serveur, `import "server-only"` pour la partie qui lit le secret)
- Format : `/paiement?ref=AN-2026-0142&montant=119&libelle=Le%20Complet%20M&encaisseur=A&exp=…&sig=…`.
- Montant en euros, entier ou avec deux décimales au plus (`119`, `119.5`, `119.50`) ; converti en centimes entiers pour tout calcul ; contrôlé côté serveur entre 15 € et 600 € (bornes dans src/data/ ou src/config/, source unique).
- `ref` au format AN-AAAA-NNNN (réutilise le motif de src/lib/reservation/reference.ts) ; `libelle` 1 à 80 caractères, sans caractère de contrôle ; `encaisseur` A ou B ; `exp` en secondes Unix, 7 jours après la génération.
- Signature HMAC-SHA256 (node:crypto) avec `PAYMENT_LINK_SECRET` (au moins 32 caractères, sinon erreur claire côté serveur), sur une chaîne canonique non ambiguë qui couvre ref, montant normalisé en centimes, libellé, encaisseur et expiration, avec un préfixe de version (`v1`). Encodage base64url. Comparaison en temps constant (`timingSafeEqual`, longueurs vérifiées avant).
- Fonctions pures et exportées : `normaliserMontant`, `chaineASigner`, `signerLien({ref, montant, libelle, encaisseur}, maintenant)` → URL relative, `verifierLien(params, maintenant)` → `{ valide: true, lien }` ou `{ valide: false, raison: "format" | "signature" | "expire" | "montant" }`. Le secret est passé en paramètre aux fonctions pures, lu depuis l'environnement par une petite couche serveur.
- Tests Vitest obligatoires (brief 15.1) : signature valide ; signature falsifiée ; chaque champ modifié après signature (ref, montant, libellé, encaisseur, exp) ; lien expiré ; montant hors limites (14,99 €, 600,01 €, négatif, texte) ; `119` et `119.00` signent pareil ; caractères spéciaux et accents dans le libellé ; absence de secret.

## 2. Page d'administration `/admin/lien-paiement`
- Protégée par mot de passe (`ADMIN_PASSWORD`), `noindex`, hors sitemap, `Disallow` dans robots, utilisable sur téléphone.
- Protection : authentification HTTP Basic dans `src/proxy.ts` (Next 16 a renommé middleware en proxy : lis node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md), limitée à /admin/:path* et /api/admin/:path*, avec comparaison en temps constant compatible avec le runtime du proxy (pas de node:crypto si le runtime ne le permet pas : compare des empreintes SHA-256 via Web Crypto). Sans `ADMIN_PASSWORD` : 503 « Administration non configurée », jamais d'accès ouvert. La route d'API de génération revérifie elle-même l'en-tête Authorization (défense en profondeur). En-tête `Cache-Control: no-store` sur ces réponses.
- Formulaire : référence (préremplie avec `AN-<année>-`), montant, libellé (suggestions formule × gabarit depuis src/data/offres.ts, par ex. « Le Complet M » ; saisie libre possible), encaisseur A ou B (avec le nom de l'associé depuis la config, ou l'emplacement « à compléter »), téléphone du client facultatif (pour WhatsApp et SMS).
- Génération côté serveur (`POST /api/admin/lien-paiement`), réponse avec l'URL absolue (site.url) et la date d'expiration.
- Boutons « Copier » (presse-papiers, avec repli si refusé), « Envoyer par WhatsApp » (`https://wa.me/<numéro>?text=…` ou `https://wa.me/?text=…` sans numéro), « Envoyer par SMS » (`sms:<numéro>?&body=…`). Message type : « Bonjour, voici le lien sécurisé pour régler votre prestation Allée Nette (réf. …, … €) : … Il est valable 7 jours. » Annonce de l'état pour les lecteurs d'écran.

## 3. Page `/paiement`
- Composant serveur : les paramètres sont lus et vérifiés côté serveur (le secret n'est jamais envoyé au navigateur). Respecte cacheComponents (lecture des searchParams dans une frontière Suspense, voir la doc installée).
- Lien absent : explication courte (« Vous avez reçu un lien de paiement par message… ») et contacts. Lien invalide, falsifié ou expiré : paiement refusé, message adapté à la raison (expiré : « demandez-nous un nouveau lien »), contacts (téléphone, WhatsApp, e-mail via src/lib/contact.ts), aucun bouton de paiement.
- Lien valide : récapitulatif (prestation, montant, référence), « Paiement à [Prénom Nom] EI, SIREN […] » depuis `site.associes[encaisseur]` (emplacements « à compléter » sinon), mention `site.mentionTva`.
- Bouton principal « Payer [montant] € en ligne » → `POST /api/paiement/session` avec les paramètres signés → le serveur revérifie le lien, puis crée une session Stripe Checkout avec la clé de l'encaisseur (`STRIPE_API_KEY_A` / `STRIPE_API_KEY_B`) : mode `payment`, devise EUR, une ligne « Allée Nette — [libellé] — réf. [ref] » au montant en centimes, quantité 1, `metadata: { reference, encaisseur }` (et sur le PaymentIntent via `payment_intent_data.metadata`), `locale: "fr"`, **jamais de `payment_method_types`** (moyens de paiement dynamiques, gérés depuis le tableau de bord Stripe : cartes, Apple Pay, Google Pay, PayPal), `success_url` = `/paiement/merci?ref=…&encaisseur=…&session_id={CHECKOUT_SESSION_ID}`, `cancel_url` = le lien de paiement d'origine. Si le type du SDK installé l'accepte (version d'API de stripe 23.0.0), ajoute `integration_identifier` avec une étiquette constante du type `allee-nette-lien-signe-` suivie de 8 lettres aléatoires choisies une fois pour toutes. Le navigateur est ensuite redirigé vers l'URL de la session. Clé d'idempotence dérivée de la signature et de la minute en cours (évite deux sessions sur un double clic). Limite de débit en mémoire. Événement `paiement_initie`.
- Client Stripe : une instance par encaisseur (`new Stripe(cle)` ou la classe client exportée par le SDK installé), créée côté serveur seulement ; jamais le motif global déprécié. Clés recommandées : **clés restreintes** (`rk_test_…` / `rk_live_…`) avec le minimum de droits (Checkout Sessions en écriture, PaymentIntents et Charges en lecture pour le webhook) ; les clés secrètes `sk_…` restent acceptées. Ne journalise jamais une clé, ni dans les logs ni dans les messages d'erreur.
- Clé absente pour cet encaisseur : le bouton est remplacé par « Paiement en ligne bientôt disponible » et les contacts ; jamais d'erreur brute. Clé de test (`sk_test_` ou `rk_test_`) : petit bandeau « Mode test : aucun débit réel ». Clé réelle (`sk_live_` ou `rk_live_`) hors production (`CONTEXT !== "production"`) : refus, pour ne jamais encaisser depuis un aperçu.
- Bouton secondaire PayPal, seulement si `PAYPAL_ENABLED=true` et si les identifiants de l'encaisseur existent : SDK JavaScript PayPal chargé avec @paypal/paypal-js, uniquement après un clic sur « Payer avec PayPal » (aucun script tiers ni cookie PayPal tant que le client ne l'a pas demandé) ; création de la commande côté serveur (`POST /api/paiement/paypal/commande`, API Orders v2, intent CAPTURE, montant issu du lien vérifié, `custom_id`/`invoice_id` = référence) et capture côté serveur (`POST /api/paiement/paypal/capture`) ; `PAYPAL_ENV=sandbox|live`, `PAYPAL_CLIENT_ID_A|B` (identifiant public, transmis au navigateur), `PAYPAL_CLIENT_SECRET_A|B` (serveur uniquement). Après capture réussie : e-mail à l'associé concerné et page de remerciement.
- Bloc « Payer sur place après la prestation » : carte et sans contact (Apple Pay, Google Pay) sur notre terminal mobile, PayPal par QR code, espèces ; facture remise ou envoyée par e-mail. Réutilise PAIEMENT_SUR_PLACE et les données existantes.
- Logos des moyens de paiement : le brief exige les logos officiels, jamais redessinés. Les sites des émetteurs sont injoignables d'ici : crée un composant `LogosPaiement` qui affiche les fichiers officiels s'ils sont présents dans `public/paiement/logos/` (noms de fichiers documentés), et sinon des libellés texte sobres (« CB », « Visa », « Mastercard », « Apple Pay », « Google Pay », « PayPal ») — jamais un dessin imitant une marque. Documente dans `public/paiement/logos/LISEZMOI.md` où télécharger chaque logo officiel et ses règles d'usage.
- Texte de réassurance : « Paiement sécurisé par Stripe. Nous ne voyons ni ne conservons vos données bancaires. »
- Page `noindex`, hors sitemap, en-tête `Cache-Control: no-store`, `Referrer-Policy: no-referrer` (le lien contient la signature).

## 4. Après le paiement
- Webhook Stripe : `POST /api/stripe/webhook/[encaisseur]` (A ou B) : corps brut (`request.text()`), vérification de la signature avec `STRIPE_WEBHOOK_SECRET_A|B` (`stripe.webhooks.constructEventAsync`), refus 400 sinon. Événements `checkout.session.completed` (si `payment_status === "paid"`) et `checkout.session.async_payment_succeeded` → e-mail à l'associé concerné (`site.associes[encaisseur].email`, via Resend et l'expéditeur de l'étape 6) : référence, montant, moyen de paiement (type récupéré sur le PaymentIntent, ex. card, paypal ; portefeuille Apple Pay / Google Pay si disponible), date, identifiant de session. `checkout.session.async_payment_failed` → e-mail d'alerte. Autres événements : 200 sans action. Répondre 200 rapidement ; une erreur d'envoi d'e-mail est journalisée (sans donnée personnelle) et renvoie 500 pour que Stripe réessaie.
- Page `/paiement/merci` (`noindex`) : si `session_id` et `encaisseur` sont présents et que la clé existe, le serveur récupère la session pour afficher l'état réel (payé, en cours de traitement, non payé) ; sinon texte générique. Confirmation, rappel du rendez-vous (« nous vous confirmons l'heure par message »), rappel que la facture suit (par e-mail). Événement `paiement_reussi` côté navigateur une seule fois quand le statut est payé.

## 5. Configuration et documentation
- Garde-fou contre la fuite de clés : un test Vitest parcourt les fichiers suivis par git (`git ls-files`) et échoue s'il trouve une chaîne du type `sk_live_`, `rk_live_`, `sk_test_`, `rk_test_` ou `whsec_` suivie d'au moins 10 caractères alphanumériques (les exemples de documentation utilisent `sk_test_...` tronqué). Les webhooks sont obligatoires, pas facultatifs : la documentation le dit clairement.
- `.env.example` : ajoute `PAYMENT_LINK_SECRET`, `ADMIN_PASSWORD`, `STRIPE_API_KEY_A`, `STRIPE_API_KEY_B`, `STRIPE_WEBHOOK_SECRET_A`, `STRIPE_WEBHOOK_SECRET_B`, `PAYPAL_ENABLED`, `PAYPAL_ENV`, `PAYPAL_CLIENT_ID_A`, `PAYPAL_CLIENT_SECRET_A`, `PAYPAL_CLIENT_ID_B`, `PAYPAL_CLIENT_SECRET_B`, avec un commentaire en français pour chacune (où la trouver, test ou réel, comment générer un secret : `node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"`).
- Aucune de ces variables ne doit être préfixée `NEXT_PUBLIC_` ni atteindre le JavaScript du navigateur (vérifie le build : rechercher `sk_test`, `whsec`, le nom des variables secrètes dans .next/static).
- `docs/paiement.md` : notes techniques pour le README de l'étape 10 (création des deux comptes Stripe, activation d'Apple Pay / Google Pay / PayPal dans le tableau de bord, déclaration des deux webhooks avec leurs URL, passage en mode réel, options de paiement sur place, rappel de vérifier les frais : le modèle financier compte 1 %).
